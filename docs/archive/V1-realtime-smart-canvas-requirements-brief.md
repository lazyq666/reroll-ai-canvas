# Infinite Canvas V1：实时多人互动画布需求简述

> 文档状态：Draft v0.1
> 创建日期：2026-07-23
> 适用版本：V1 初版
> 目标规模：单画布同时在线编辑不超过 5 人

## 1. 背景

Infinite Canvas 已具备账号、画布权限、智能节点、Connection、Smart Group、Frame、生成任务和画布持久化能力，但当前编辑模型仍以单客户端保存完整画布快照为主。

V1 希望让小团队成员同时进入同一张智能画布并进行编辑。交互感受参考 Figma，但初版重点是“操作及时可见、画布状态一致、不会互相覆盖”，不是一次性复刻 Figma 的全部协作能力。

## 2. 产品目标

- 最多 5 名有编辑权限的用户可以同时打开并操作同一张 Smart Canvas。
- 一名用户提交的有效画布操作能实时出现在其他用户页面。
- 不同用户编辑不同 Node 时互不覆盖。
- 多人同时编辑同一对象时，所有客户端最终得到相同且可解释的结果。
- 断线重连后自动恢复到服务端最新 Canvas Revision，不需要用户刷新页面。
- 保留现有单人画布的主要操作习惯和 Figma 式指针、抓手、框选及快捷键体验。

## 3. 成功标准

- 5 个客户端连续协作 30 分钟后，Node、Connection、Smart Group、Frame 和 Generation Output 状态一致。
- 不出现“后保存的完整快照覆盖其他用户已完成操作”的情况。
- 同一操作因网络重试被重复发送时只生效一次。
- 已被删除的 Node 不会被迟到的移动、改名或生成结果重新创建。
- 正常网络下，已提交操作在其他客户端可见的 P95 延迟不高于 500ms。
- 客户端重连完成后 3 秒内追平服务端最新 Canvas Revision。

## 4. 用户与权限

- 沿用现有账号和画布权限体系。
- 管理员和对目标画布有编辑权限的设计师可以参与实时编辑。
- 游客、匿名分享访问者和只读分享页不能加入编辑通道，也不能提交 Canvas Mutation。
- 服务端必须对每次实时操作重新验证用户身份、画布权限和目标画布 ID，不能只在建立连接时验证一次。

## 5. 首版同步范围

首版同步的是“已经提交的画布结果”，包括：

- 创建、复制和删除 Node。
- 移动、缩放和修改 Node 属性后的最终结果。
- 创建、删除和修改 Connection。
- Smart Group 的创建、解散、成员加入、成员移出、排列和图片吸收。
- Frame 的创建、移动、缩放、改名、颜色变化、空间成员变化及删除语义。
- Prompt、文本、循环配置和生成设置等持久化字段的修改。
- Generation Run 的已提交状态、Pending Node、进度状态和 Generation Output。
- 画布标题及其他属于共享文档的数据。

拖动和缩放手势只在操作结束后同步最终值；首版不广播每一帧位置。

## 6. 首版明确不做

- 实时光标。
- 实时选区和选框。
- 拖拽或缩放过程中的实时位置。
- 在线成员头像、成员列表和进入/离开提示。
- 评论、批注、跟随他人视角和演示模式。
- 离线编辑后的复杂自动合并。
- 超过 5 人的容量与压力目标。
- 多实例、多 Worker 或跨服务器部署下的分布式协作。
- 完整版本历史、分支、时间旅行和管理员审计面板。

以下状态始终属于客户端本地状态，不进入 Canvas Sync：

- Viewport、缩放比例和 Minimap 视口。
- 当前选中 Node、选中媒体和框选范围。
- 当前工具、临时抓手和按键状态。
- 打开的弹窗、右键菜单、编辑器面板和 Hover 状态。
- 尚未结束的拖动、缩放、画笔和 Frame 绘制手势。

## 7. 核心协作规则

### 7.1 服务端权威顺序

- 服务端为每个被接受的 Canvas Mutation 分配唯一顺序和新的 Canvas Revision。
- 客户端不能通过上传旧的完整画布快照覆盖更新版本。
- 所有客户端按服务端确认顺序应用操作，并最终收敛到同一状态。

### 7.2 不同对象并行

- 用户 A 移动 Node A、用户 B 修改 Node B 时，两项操作都必须保留。
- 新增不同 Connection、创建不同 Node 或修改不同属性时，不应互相覆盖。

### 7.3 同一对象冲突

- 同一 Node 的不同属性可以分别合并，例如一人改标题、另一人改位置。
- 同一属性被多人同时修改时，以服务端确认顺序决定最终值；所有客户端必须显示相同结果。
- 删除优先于迟到的更新。Node 删除后，针对旧 Node 的移动、改名、入组或生成回写必须被拒绝或安全忽略。
- 删除 Frame 时，必须继续遵守 Smart Container 定义的“级联删除内容”与“仅删除外框”两种明确语义。
- Smart Group 成员关系必须去重，不能产生自包含、循环包含或同一成员重复出现。
- Connection 必须去重，不能产生自环或指向不存在 Node 的悬空关系。

### 7.4 幂等与重试

- 每个客户端操作具有稳定的 operation ID。
- 网络重试、页面恢复或重复消息不能导致重复 Node、重复 Connection、重复图片或重复 Generation Run。
- 客户端收到自己的服务端确认时，应确认本地操作，而不是再次执行一遍。

### 7.5 Undo/Redo

- 多人模式不得使用旧的整画布快照 Undo 覆盖他人操作。
- Undo 只撤销当前用户自己最近提交且仍可安全反演的操作，并以新的 Canvas Mutation 广播。
- 如果某项操作已经因后续协作变化无法安全撤销，界面应明确提示，而不是恢复旧快照。

## 8. 连接、重连与异常处理

- 打开画布时先获取当前 Snapshot 和 Canvas Revision，再订阅后续实时操作。
- 客户端发现 Revision 不连续时必须暂停提交、拉取缺失操作或重新加载最新 Snapshot。
- 连接中断后的前 5 秒不应打断普通画布编辑，也不显示状态提示；本地修改持久化到当前浏览器的待同步队列，页面刷新后仍可恢复。
- 连接持续中断时显示轻量“连接恢复中”状态，Viewport、选择、浏览和普通画布修改仍可继续；Generation Run、抠图等具有外部副作用的任务暂停提交。
- 重连成功后先追平服务端状态，再把待同步修改按结构化 Canvas Mutation 补交；远端已删除对象不能被待同步更新复活。
- 无法恢复时提供明确错误和手动重试入口，不能静默退回可能覆盖远端数据的旧保存模式。

## 9. Generation Run 协作要求

- 一名用户启动 Generation Run 后，其他客户端能看到对应 Pending Node 和状态变化。
- 同一个 operation ID 只能提交一次实际生成任务，重试连接不能重复计费或重复生成。
- Generation Output 回写前必须确认目标 Node 仍存在且运行仍有效。
- 如果目标 Node 已删除，迟到结果不得复活该 Node；结果可以进入可恢复记录，但不能直接写回共享画布。
- 多人编辑 Prompt 或 Generation Settings 时，运行使用启动瞬间确认的输入快照，之后的修改只影响下一次运行。

## 10. 交互要求

- 保持现有 Figma 式 Pointer、Hand、Space 临时抓手、框选、多选和快捷键。
- 远端操作到达时，不应打断当前用户的输入焦点、Viewport 或本地选择。
- 远端删除当前正在编辑的 Node 时，应结束本地编辑并给出明确提示。
- 远端移动或修改未被本地操作占用的 Node 时，界面平滑刷新，不整页闪烁。
- 首版不展示是谁进行了修改；只保证结果实时出现。

## 11. 技术边界

- 共享状态必须通过结构化 Canvas Mutation 表达，不能继续以整画布覆盖保存作为多人写入协议。
- `Canvas Mutation Module` 负责 Node/Connection 原子变更。
- `Smart Container Module` 负责 Smart Group 和 Frame 的容器语义。
- Viewport、Selection 和进行中的 Interaction 必须与共享 Canvas 数据分离。
- Canvas Persistence 负责 Snapshot、Canvas Revision、断线追平和持久化，不应重新实现业务操作语义。
- 实时传输可以使用现有 WebSocket 基础设施扩展，但需求不预设必须使用 CRDT 或 OT；技术方案只要满足确定顺序、幂等、冲突处理和最终一致性即可。

## 12. 验收场景

1. 两人同时创建不同 Node，双方最终都看到两个 Node。
2. 一人移动 Node A，另一人修改 Node B 标题，两个结果都保留。
3. 两人同时修改同一 Node 标题，所有客户端最终标题一致。
4. 一人删除 Node，另一人的迟到移动操作不会让 Node 复活。
5. 两人同时新增同一 Connection，最终只保留一条。
6. 一人将 Prompt 加入 Smart Group，另一人移动该 Smart Group，成员关系和位置结果均有效。
7. 一人删除 Frame 及内容，其他客户端同步删除其后代 Node。
8. 一人仅删除 Frame 外框，其他客户端仍保留 Frame 内 Node。
9. 一人启动 Generation Run，其他客户端看到 Pending 和最终 Generation Output，任务只执行一次。
10. 客户端短暂断网后可以继续普通画布编辑；恢复连接后自动追平并补交待同步 Mutation，不覆盖离线期间其他人的无关修改，也不复活已删除 Node。
11. 一名用户 Undo 自己的移动操作，不回滚其他用户之后创建的 Node。
12. 5 个客户端持续随机执行创建、移动、改名、连线和分组操作，最终 Snapshot 一致。

## 13. 推荐实施阶段

### 阶段 A：完成组件化边界

- 继续抽离 Viewport、Selection 和 Interaction。
- 确保所有共享写操作最终进入 Canvas Mutation。
- 禁止 UI 事件处理器直接散落修改共享 Nodes。

### 阶段 B：操作协议与单连接闭环

- 定义 operation ID、actor ID、base revision、操作类型和 payload。
- 服务端按画布串行接收、校验、应用、持久化和广播。
- 完成单浏览器双标签页验证。

### 阶段 C：冲突、Undo 与生成任务

- 实现属性级冲突规则、删除优先、去重和幂等。
- 把 Undo 改为用户操作的反向 Mutation。
- 接入 Generation Run 状态和迟到结果保护。

### 阶段 D：5 人稳定性验收

- 进行 5 客户端并发和断线重连测试。
- 验证延迟、最终一致性、任务幂等和长时间运行稳定性。

## 14. 主要风险

- 旧代码仍存在直接修改 Nodes 的路径，可能绕过统一操作协议。
- 现有整画布 Snapshot Undo 会覆盖远端更新，必须在多人模式前替换。
- Smart Group 图片吸收和 Frame 空间归属属于复合操作，必须作为一个原子业务操作处理。
- Generation Run 具有异步和计费副作用，重复提交风险高于普通画布操作。
- 客户端本地状态与共享状态如果边界不清，会错误同步 Viewport、Selection 或半完成手势。
- 当前服务以单进程部署为前提；扩展到多 Worker 前需要额外的共享消息与顺序机制。
