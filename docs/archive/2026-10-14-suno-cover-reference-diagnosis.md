# Suno 参考效果故障：Cover 语义与音频直链

- Status: Archived
- Current: [Suno 音乐实验室](../current/suno-music-lab.md)

## 已确认的本地问题

用户明确说明官网使用 Remix–Cover。当前用户 Workspace 的 test、test2、test3 实际操作均为 inspo。
最近 test3 上游任务为 `task_01M4W6F827ECQ7CFPRPRH7C453`，参考权重 .89 确实保存。
界面此前通过“人声/纯音乐”决定 inspo/cover，无法独立表达 Cover 意图。
[Suno Cover 说明](https://help.suno.com/en/articles/2872257)的目标是改换风格并保留旋律；
[Inspire 说明](https://help.suno.com/en/articles/6882753)则是在参考风格下创作新曲。
因此调高 Inspire 的权重不能替代用户要求的 Cover。

浏览器回归先出现 `Cover intent must survive switching between vocals and instrumental` 失败，
修复后通过。添加独立 Cover/Inspire 控件，默认 Cover；音乐类型独立，兼容人声及纯音乐 Cover。
历史与复用保留实际操作；不会将旧 Inspire 记录伪装成 Cover。
人声 Cover 的歌词保持为 prompt，仅 style 映射 tags；纯音乐仍将描述与风格合并 tags。
字段依据 [APIMart Upload Cover](https://docs.apimart.ai/en/api-reference/audios/suno/upload-cover)。

第二个问题在真实上传路径复现：用户 music.mp3 的 Managed Media 与原文件逐字节一致，
均为 3,235,681 bytes，SHA-256 为 `d91c1fca4c0e0d77248c446147b36bebc45afcd622d2a228ae385ee0e728f550`。
但当时 Litterbox 对原音频和小测试音均返回 HTTP 500；备用 temp.sh 返回一个可访问 URL，
GET 实际是 3,528 bytes HTML 下载页，POST 才返回音频。原代码只检查 URL 外观，会把下载网页提交给上游。
历史没有保存临时链接，因此不能倒推每条旧记录都使用过这个错误地址。

修复后，收费前用不带凭据的 GET 回读，完整字节数和 SHA-256 必须与原文件相同；
超量、截断、同长度损坏、网页和不可读链接都不能进入生成提交。
首选 Litterbox，用户另行明确授权 tmpfiles.org 为备用临时托管，存储六小时。
[备用托管 API](https://tmpfiles.org/api)返回文件页，需要解析实际下载链接，不能拼出不存在的直链。
下载签名实测约五分钟，短于文件保存期；每次生成前现取现验，不缓存到历史。
上游排队后延迟读取仍可能超时，此时不会自动重提收费任务。

## 真实效果验证

第一次用户音频探针 `run_33cbb22b96554ca9b8ca10824e8cecd3` 在额外验收校验器内拦截了 HTML，
没有调用收费接口。修复后的用户音频提交为 `task_01M4WEQEBM6ZKTD19M11WYVDAX`，
V6、uploadCover、custom=true、instrumental=true、audio_weight=.89；直链回读内容与原文件完全一致。
上游五秒后明确返回内容审核未通过，`credits_cost=0`、`cost=0`。
没有返回成品，没有通过反复改写提示词尝试绕过该拒绝；也无法从通用错误确定是音频、提示词、版权或其他原因。
本地已增加对应双语错误，避免只显示无法解释的失败。

为检验音乐参考而不是仅验证通信，另制作了原创 117 BPM、34.82 秒的旋律、低音、和声和打击乐合成片段。
提交文本只写 Piano instrumental，没有写出音符序列；仍用 V6、Cover、audio_weight=.89。
任务 `task_01M4WEZTC3V55YCWBSD30GAVHP` 返回 94.8、92.8 秒两首音频，费用共 0.5 Credits。
一次查询连接中断后仅继续查询原任务，没有重新提交。

对音频提取按时间排列的十二音级特征，减弱固定音色包络的影响，搜索 0.8–1.2 倍时间伸缩和移调。

- 真实页面回归覆盖独立参考方式、人声/纯音乐切换、Cover 与 Inspire 的实际端点、历史标签与复用、双语动态提示。
- 文档、缓存和共享资源检查同步执行。最终命令与结果记录在 LAZ-85。
- 用户 music.mp3 尚未通过上游审核，也没有得到其官网对照成品，不能宣称该文件已生成成功或与官网相同。
- 人声 Cover 参数与页面链路通过自动回归；本次真实音乐效果只测试纯音乐 Cover，不宣称所有版本或模式都经过付费试听验收。

## 继续调查：独立上传与错误分类（2026-10-14）

用户进一步确认：Suno 官网也是重新上传同一份本地 music.mp3，再执行 Remix → Cover；
不是直接复用曲库中已有歌曲。此为用户报告，未取得官网原始网络回执。

### 单变量隔离

[APIMart 独立上传合同](https://docs.apimart.ai/en/api-reference/audios/suno/upload)只接受
`audioFilePath`，无需版本、提示词、风格、权重或 Cover 模式。本轮直接调用该官方端点，
绕过本地表单与生成参数映射，提交前均以无凭据 GET 校验完整音频字节。

| 对照 | 输入／变量 | APIMart 结果 | 耗时 | Credits |
| --- | --- | --- | --- | --- |
| 原文件独立上传 | 原始 music.mp3，fresh tmpfiles 直链，仅 audioFilePath | `task_01M4WGKBF1HA33VAS554QZY1MQ`，内容审核拒绝 | 2 秒 | 0 |
| 格式／托管正对照 | 自制原创旋律，MP3、44.1 kHz、双声道、192 kbps、约 134.8 秒，同一 tmpfiles、同一上传端点 | `task_01M4WGM7PCW0GP2C8NXDZDJA0K`，completed，返回 audio_id | 24 秒 | 0.04 |
| 失效链接负对照 | 上一轮原创 WAV 的过期签名链接，GET 实际为 HTTP 200、2980 bytes HTML | `task_01M4WGRS7W22D940BT1TW8DXWT`，文件无效或格式不支持 | 6 秒 | 0 |

原文件为 3,235,681 bytes，SHA-256 与前文一致，ffprobe 为 134.817958 秒，
ffmpeg 完整解码无错误；远低于 Cover 文档的 8 分钟限制。
格式正对照为 3,236,929 bytes，时长/声道/采样率/目标码率匹配，但音频内容不同；
它证明当前接口、凭据和该托管的 MP3 路径可以成功，不证明每一种 MP3 编码特征都等价。
原文件新链接在提交前约剩 297 秒签名有效期，2 秒即失败；旧 Cover 请求也在签名期限内失败。
失效链接负对照在首个检查中因仅验证 HTTP 状态而被断言拦截，没有提交；
确认 HTTP 200 实际为 HTML 后才提交一次。应用现有完整字节校验可识别此类假成功，未修改实现。

本轮没有再次提交 Cover，没有修改原文件或尝试改变其音频指纹。三个独立上传诊断合计 0.04 Credits。

### 能排除什么，不能排除什么

- 同一原文件在完全没有生成参数的独立上传中仍收到相同拒绝，说明至少存在生成之前的文件导入／审核问题；
  不能靠调整 Cover 权重、风格文字、版本或人声开关解决这个已复现的上传拒绝。
- 同托管、近似同大小、同格式和时长的原创对照成功；过期 HTML 链接收到另一种错误。
  因此通用 MP3 不支持、托管整体不可用、普通过期链接被统一误标审核等解释不符合本轮证据。
- 本机下载一致不等于能观测 APIMart 服务器实际收到的字节；没有供应商下载日志，
  仍不能形式上排除对原文件路径特定的远端取回问题。
- 用户单独授权了一次 Litterbox 一小时托管对照；该服务仍返回 HTTP 500，没有得到可提交的直链，
  因此“同一原文件、另一家托管”的对照未完成，也没有为此调用 APIMart。
- 目前最窄的定位是 APIMart 音频导入／审核链路对该文件的特定拒绝。
  通用 `task_failed` 回执没有审核子码，不能断言为版权命中、内容违规、APIMart 自身误判、
  上游 Suno 账号／策略差异，或某个明确的供应商程序缺陷。
  官网成功不保证另一供应商链路使用相同账号上下文与审核过程；这一差异是待核实假设。
