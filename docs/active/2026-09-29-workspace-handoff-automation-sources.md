# 两设备工作区交接自动化：研究与一手资料

> 后续决策：用户选择 A 点击一次关闭、B 启动自动验收。下文包含较早的全自动协同候选；最终交付以[在线交接规格](2026-09-29-online-workspace-handoff.md)为准，不实现 B 请求 A 自动关闭。

- 日期：2026-09-29
- 状态：研究；未改变实现或已接受的交接合同
- 关联：[LAZ-69](https://linear.app/lazyq/issue/LAZ-69)、[ADR-0017](../adr/0017-offline-workspace-handoff.md)、[当前实现与待验收范围](2026-09-27-workspace-handoff.md)
- 证据标签：**现状**来自仓库；**官方事实**来自下列一手资料；**设计建议/推断**尚未实施或实测。

## 给使用者的结论与方案选择

**可以自动化。用户已确认两台通常都开着并联网，希望零次交接点击；备用操作是点一次“关闭本服务器”。因此优先验证“B 打开工作区时，自动请求 A 安全交出编辑权”；无法自动交接时保留一键关闭。** 当前交接编号用于证明接收端拿到的是指定版本；自动化应把这个证明交给程序，保留完整文件核验。

研究范围是当前 OneDrive + 本地 SQLite 轮换工作区。两台通常在线已确认，操作系统组合和 OneDrive 账号类型尚未核实。本文是研究建议，不是已实现功能或已接受架构决定。

| 方向 | 日常体验 | 改动与前提 | 本次判断 |
| --- | --- | --- | --- |
| 独立在线交接服务 + 现有 OneDrive | B 打开时请求 A 自动交接；忙碌时等待，备用一键关闭；免记、免输编号 | 两台一次性配对；新增小型在线服务和客户端状态流程，文件继续走 OneDrive | 最适合保持本地速度的近期方案 |
| 两台直接通信 + 现有 OneDrive | B 直接请求 A 保存和交出，正常路径同样免点击 | 两端接收程序必须可达；跨网络可评估 Tailscale，需保存独立于同步目录的交接回执 | 不想维护云端服务时的候选；上一台不可达便不能新建自动交接 |
| Microsoft Graph 承担在线交接通道 | 理想体验同上 | Microsoft 登录授权、应用注册、账号差异；必须验证协调协议，不能只读取同步文件 | 值得验证，但尚不能承诺是更简单的替代 |
| 两台访问同一套常驻 Reroll | 打开同一个地址继续工作，消除数据搬运式交接 | 一台主机持续在线，Workspace 与服务同机；本地生成工具及网络体验需核实 | 真正想取消交接动作时优先考虑 |
| 仅数据库放云端，媒体继续 OneDrive | 数据记录无需搬运，媒体仍要到齐 | 仓库已有 Turso 试用，但仍有网络、媒体与双设备验收成本 | 不是仅为省输入编号的首选 |
| 同步目录里自动读取编号、按修改时间选最新版 | 表面无操作 | 无法区分完整旧副本与最新版本 | 不满足现有保护目标 |

常驻方案可用 Tailscale Serve 将本机服务经 HTTPS 提供给同一私有网络内的设备；它解决连接，不提供主机常在线或应用本身的可靠性。官方来源：[Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve)。数据库上云的当前边界见 [ADR-0014](../adr/0014-optional-cloud-sqlite-authority.md)，不把过去试用记录当成本次用户的实际配置。

两台直接通信是另一种设计推断：由配对的当前持有者直接提供指定 seal，并以持久的请求、交出和接收回执协调。它不必部署独立云端登记服务，但同样不能直接相信同步目录；必须处理双方启动、交出后应答丢失和原机恢复，无法判定持有者时两端停写。Tailscale 只提供可达通道，不自动实现这些规则。下面以独立协调服务展开，因为它能在 A 完成发布后离线、B 稍后接续时保留可查询的交接状态。

### 建议的交互：默认自动，必要时一键关闭

1. 首次配对两台设备，核实相同 Workspace、当前可信版本和兼容客户端，并开启“换设备自动接续”。凭据留在 Device State。
2. B 启动或明确打开这个工作区时，向在线协调服务提交一次接续请求。普通网页刷新、后台轮询、窗口焦点变化不能反复触发，避免两台来回抢占。
3. A 的常驻接收模块收到请求，检查所有画布客户端和后台任务。草稿需通过现有保存机制取得确认；其他仍在编辑的协作者、无法应答的页面、上传和生成任务会阻止立即交接。默认等待或提供取消，不强行关闭。
4. 条件满足后，A 自动保存、冻结新写入、排空任务与连接、封存并发布交接版本；A 页面显示已切到另一台，停止编辑。B 自动等待本地文件到齐并核验全部清单。
5. B 原子取得编辑权并正常打开，A 完成本次停服。A 若需要保持进程以回复状态，只能留在维护状态；它的旧页面和本机恢复回执不能重新开放写入。
6. 自动路径被阻挡时，用户可在 A 点一次“关闭本服务器”，调用同一套安全保存、封存、登记和停服流程。存在未完成生成或保存失败时，该按钮仍须等待或解释失败，不能硬杀进程后宣称交接成功。

这意味着日常动作只剩下在下一台打开 Reroll，不再额外点击交接。它需要新增经过身份校验的设备请求通道，以及 A 端可响应的本地程序；“电脑在线”不等于 Reroll 接收模块正在运行。可以由当前服务持有到交接结束，或在需要停服后继续收发的场景由启动器承担。在线请求必须转换为现有本机受控操作，不能把管理员接口直接公开到互联网。

这里“已登记交接”只表示在线服务收到版本信息，**不表示 OneDrive 已上传全部素材**。两台同时在线时，可由 B 确认完整收到，形成真正的接续成功回执。若 A 使用备用关闭且 B 未打开，要显示“现在可以关机”，仍须另行验证云端文件完整可取；没有文件级证据时，应要求等待 OneDrive 上传结束。A 过早休眠而文件尚未上传时，B 应等待，不能打开旧版。

### 在线服务究竟保存什么

只需保存工作区标识、配对设备、当前编辑设备、递增代次、交接编号、清单摘要和操作回执，不需要把画布数据库或图片搬进去。它像一份两台电脑共同查询的“使用登记表”。

建议状态顺序为：A 持有编辑权 → A 停写并封存 → 发布指定版本 → B 核验文件 → B 条件取得编辑权。每次转换要求原 owner 和代次仍匹配；重复请求复用同一个操作 ID，网络超时后先查询实际结果，避免重复交接或误恢复 A 的写入。

第一版不靠“几分钟没心跳”自动换 owner。上一台休眠或失联不证明它已停写、清空任务和上传；租约过期也不能让未上传的数据凭空出现。A 发布结果不确定时保持停写；B 抢占成功但未启动时保留可恢复回执。旧 owner 重新打开时必须重新确认在线状态，不能仅凭旧本机回执恢复。该协议假设配对设备都使用支持此规则的可信客户端。

Cloudflare Durable Objects 的事务和强一致持久存储可作为实现候选；也可用能完成同等条件更新的数据库服务。此为架构建议，未部署、未实测两处网络可达性，也未给出免费额度或费用承诺。[官方存储合同](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/)

### “直接合盖也不用管”的边界

关闭浏览器、操作系统休眠与正常应用退出不是同一事件。浏览器 beforeunload 并不保证每次触发，不能用它承担唯一交接承诺；可以提前保存、辅助提醒，但保存和上传仍需要执行时间。[浏览器事件文档](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)

针对用户已确认的两台在线场景，推荐上述 B 发起、A 协同响应的自动流程；这仍要求 A 程序实际运行并回应，所有未保存内容获得保存确认。若希望上一台随时合盖而下一台照常继续，常驻单服务或持续云端权威是更匹配的架构，仍只能保证已经确认保存的数据。

### 后续实施前的验证

先在隔离工作区做小型协议验证，不迁移正式数据。最低覆盖：

- A 已登记但图片未上传；B 的目录完全自洽却是旧版本；交接标记先于数据库到达。
- A/B 同时申请、同机多进程、重复请求、服务已提交但响应丢失、接管后进程崩溃。
- A 合盖后恢复、网络中断、在线记录不可读、旧客户端回流；不得通过超时或本地旧编号静默放行。
- OneDrive 冲突副本、Files On-Demand、大素材核验耗时和两种操作系统行为。
- UI 明确区分本机封存、在线登记、素材上传与接收端就绪；实现时所有状态均需中英文、主题和动态切换验收。

现有安全交接由 [LAZ-69](https://linear.app/lazyq/issue/LAZ-69) 跟踪，Linear 为 Done；其文档仍明确保留真实双设备、Windows 和大素材验收，不能据此宣称自动交接已经验证。本次只读查询现有任务，没有创建重复任务或更改其状态。自动化若进入实施，应单独跟踪新范围，并修订 ADR-0017 中“无外部协调、手工独立传号”的决定；本研究不改写它。

## 证据与技术细节

要取消手抄编号而保持原保护，需要一个不依赖本机 OneDrive 同步副本的交接确认渠道，例如独立在线协调服务，或与配对原设备直接通信的协议。它必须核实当前由哪台编辑、下一次交接的版本、以及是否已经正式交出。单纯自动读取本地或云端 `handoff.json` 都不够。

“能在线读到一个文件”和“能证明它是上一台最后交出的完整版本”是两回事：A 可能已经产生新版本，但其上传尚未到云端；此时 Graph 返回的云端旧文件与 B 的本地旧文件可能恰好一致。这个反例直接来自现有 [ADR-0017](../adr/0017-offline-workspace-handoff.md) 对旧副本与独立编号的约束，不是 Graph 的缺陷。

## 现有代码能复用什么

### 用户已有 Turso：优先评估复用账号作为交接登记

用户补充已注册 Turso。**设计建议：可以复用账号，优先考虑独立的小型交接数据库**，只放设备、交接请求、owner、代次、seal 和回执；不启用原有“画布记录上云”模式，也不覆盖原数据库。若复用同一数据库，须先核实原数据用途、表名和访问权限；已有账号不证明旧数据库与令牌仍可用。

Turso libSQL 官方提供 write 事务（BEGIN IMMEDIATE），写事务转发到主实例；可在短事务中完成核对当前 owner/sequence 与条件变更。批事务整体成功或回滚。[Turso SDK 事务文档](https://docs.turso.tech/sdk/ts/reference#transaction-modes) 因此两台可信的本机程序可直接用远端数据库登记和轮询接续请求，不必另外部署一个执行服务；自动保存、封存、核验和停服逻辑仍需在 Reroll 实现。协调判定与失败读回应走云端主实例的一致读写路径，不能用过期的本地副本放行。事务不跨越素材同步等待；轮询间隔须结合实际额度与响应要求评估。

可复用 [Turso 传输](../../backend/infinite_canvas/turso_sqlite.py) 的连接、参数化查询与事务能力；[已有租约](../../backend/infinite_canvas/turso_workspace_lease.py) 的幂等与条件变更可参考，但不能直接照搬其超时接管语义到本地 SQLite 交接。数据库凭据保存在两台各自 Device State，不能送进网页或 OneDrive。

**现状：原 Turso 入口没有删除，而是默认隐藏。** [设置接口](../../backend/main.py) 仅在当前工作区已经使用云端记录，或环境变量 `INFINITE_CANVAS_SHOW_CLOUD_RECORDS` 严格等于 `1` 时返回 `visible=true`；[设置界面](../../static/js/preferences.js) 按此值展示。接口仍要求管理员。[配置示例](../../.env.example) 明确说明默认隐藏，改配置后重启，显示入口不等于配置或启用 Turso。

本次核实当前 checkout 根目录及 backend 下均无 `.env`，工具进程也未设置上述变量；这支持默认隐藏的解释，但不能证明另一个已启动进程或另一设备的实际环境。已有连接文件是否存在与 visible 条件无关；文件只影响迁移准备资格。换源码目录还会改变默认 Device State 分区，参见 [状态目录实现](../../backend/infinite_canvas/workspace_storage.py)。此次未改变开关、重启服务或连接用户云端数据库。

验证：`.venv/bin/python -m unittest tests.test_cloud_storage_http` 六项通过，覆盖默认隐藏、精确配置值、显示不启用、已启用云模式断线仍显示和权限。本次是解释现有行为，未确认新的 UI 回归；旧历史提交检索因 partial clone 缺少对象且配置代理不可达而未完成，因此不声称查明了用户上次看到入口之后的具体变更提交。

**现状：** [WorkspaceHandoff](../../backend/infinite_canvas/workspace_handoff.py) 已有 `inventory`、`check_databases`、`_validate_sealed`、`acquire`、`seal`，分别负责全量清单、数据库检查、指定封存版本验收、会话接收和封存。接收保存本机 `activating/active` 回执，封存保存本机备份；外来 active 会话不能自动接管。界面与运行时已经负责等待画布保存、拒绝新业务写入、排空工作和停止后台任务。参见[实施说明](2026-09-27-workspace-handoff.md)。

**设计建议：** 在现有封存/验收外增加在线协调层，不用重写 Canvas 或数据库；在线服务只能决定“谁能接班、接哪个版本”，仍由本地完整清单证明“文件真的到齐”。正式实施前须更新 ADR，因为 ADR-0017 当前明确不引入外部协调。

## Microsoft Graph：可以做什么，不能直接承诺什么

### 独立读取云端交接文件：可行

**官方事实：** Graph 支持按 `drive-id/item-id` 或路径下载文件内容；个人账号和工作/学校账号均有委托读取权限。`If-None-Match` 可用于避免重复下载未变内容；下载响应通常重定向到短期预授权 URL。[Download driveItem content](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)

**设计建议：** Reroll 可通过 Graph 直接读取云端交接数据，绕开 B 的桌面同步延迟。用稳定 item ID/Workspace identity 绑定实际工作区，不靠“修改时间最新”或相似路径挑选版本。Graph 读请求不是 A 已停写、A 已发布或全工作区已上传的证明。

### 用 ETag 做条件更新：部分 API 有明确合同，不能泛化到所有上传

ETag 可理解为服务端给一个文件当前版本的“版本票”。条件更新的含义是：只有票号仍一致时才允许写入；其他设备已改动时拒绝覆盖。

**官方事实：** `PATCH /drive/items/{id}` 更新元数据明确支持 `If-Match`，版本不符返回 `412 Precondition Failed`。[Update DriveItem properties](https://learn.microsoft.com/en-us/graph/api/driveitem-update?view=graph-rest-1.0)

**官方事实：** `createUploadSession` 明确列出 `If-Match`；文档也给出显式提交上传时使用 `If-Match` 的例子。上传会话可以分块、恢复，并在完成后返回已创建/更新文件。[Create upload session](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0)

**官方事实与证据边界：** 简单 `PUT /content` 支持上传或替换小文件，但当前 v1.0 页面请求头表未承诺 `If-Match`。这不证明服务一定不支持，意味着不能仅凭这页把普通 JSON 覆盖上传设计成已验证的原子协调锁。[Upload or replace content](https://learn.microsoft.com/en-us/graph/api/driveitem-put-content?view=graph-rest-1.0)

**设计建议：** Graph 可以作为候选协调渠道，但需单独技术验证：个人/企业账号能力、两端同一 ETag 同时更新是否恰好一端成功、上传会话创建与最终提交之间的竞争、请求成功但响应丢失后的读回、元数据与内容是否绑定同一版本。不能把先 PATCH 元数据、再无条件 PUT 内容当作一个原子操作。若采用元数据保存状态，须先确认目标字段可写且两类账号均支持。

### App Folder 可减少权限，但不能自动获得工作区文件访问权

**官方事实：** `Files.ReadWrite.AppFolder` 将访问限制到应用文件夹；官方描述支持个人和工作/学校 OneDrive。用户依然可以修改、删除该目录文件，应用需处理此情况。[Using app folder](https://learn.microsoft.com/en-us/graph/onedrive-sharepoint-appfolder)

**设计建议：** 可将仅由应用经 Graph 操作的协调记录置于 App Folder，避免桌面同步程序把本地旧协调记录重新上传。该权限不意味着能读取用户另一目录中的工作区数据库或素材；若要直接验证那些云端文件，还须另行获得对应访问权限。账号登录、令牌保存/失效、权限撤销也是新增工作。

## “OneDrive 已同步完成”能否可靠自动检测

**官方事实：** 面向用户的支持文档建议到 OneDrive 网页核实上传，或查看 Finder / Explorer 的文件同步状态。[Check whether a file was uploaded](https://support.microsoft.com/en-us/onedrive/how-do-i-know-if-a-file-was-successfully-uploaded-to-microsoft-onedrive)

**官方事实：** 企业 Sync Health 是设备健康报表；设备报告约每 36 小时更新，或客户端启动约 1 小时后更新；首次启用可能等三天，强制单设备上报不受支持。[OneDrive sync reports](https://learn.microsoft.com/en-us/sharepoint/sync-health)

**研究边界：** 本次未找到 Microsoft 面向第三方应用公开承诺的、跨 macOS/Windows 的“指定目录全部字节已上传且对端全部下载”的实时桌面同步完成 API。这是检索结论，不是断言所有平台绝无可用接口。UI 图标、系统文件属性、日志可以辅助提示，但不应直接替代完整交接验收；Sync Health 明显不适合作为每次切换的实时放行条件。

**官方事实：** Graph 文件 hash 结构并非所有算法都有值；`sha256Hash` 明确不受支持，`quickXorHash` 是个人与工作/学校账号共同保证可用的值。[hashes resource](https://learn.microsoft.com/en-us/graph/api/resources/hashes?view=graph-rest-1.0)

**设计建议：** 因为当前清单使用 SHA-256，不能假设向 Graph 索取每个文件的 SHA-256 就能完成云端核验。可选择：下载云端文件重新计算 SHA-256（带宽成本较高）；由应用直接上传并确认不可变快照（改动较大）；或仅用协调服务发布精确 manifest/编号，B 自动等待本地文件逐一匹配。第三种能移除输入编号的工作，但 A 是否已经可关机仍需要上传完成证据或用户等待同步。必须区分“交接编号已在线发布”“文件上传已确认”“B 本地验收完成”三个状态。

## 小型外部协调服务：合同更直接

**官方事实：** Cloudflare Durable Objects 的存储提供事务与强一致性；每个对象有私有持久状态。[Durable Object storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

**设计建议：** 可按 Workspace identity 对应一个对象，只保存 owner、递增 sequence、handoff ID、manifest digest、操作 ID 和交接状态；不上传画布正文或素材。通过一个受认证的 HTTPS 接口，将“检查原 owner/sequence 并更改状态”在同一事务执行。需要实现设备配对、凭据、幂等重试、读回和服务故障处理。当前研究没有评估所在网络可达性或价格，不能据此承诺部署可用性及费用。

**官方事实：** Azure Blob Storage 明确提供强一致性，支持 ETag/If-Match 条件更新及 412 失败，并支持独占写租约。[Manage Blob concurrency](https://learn.microsoft.com/en-us/azure/storage/blobs/concurrency-manage)

**设计建议：** Azure 小型协调接口加一个状态 Blob 也是候选；它的条件写合同较明确。Blob 租约只能约束 Blob 写入，不能自动阻止离线设备的本地 SQLite 写入。无论选哪家服务，都必须在 Reroll 本地写入口执行所有权规则。此方案是新增协调基础设施，不是已有 OneDrive 免费附带的能力。

### 推荐的协调协议草案

以下均为**设计建议**，需故障注入测试后才能转成已支持能力。

1. 初次绑定时，两台停止编辑，明确一份完整初始工作区。协调器唯一记录 `active(A, sequence)`；旧客户端不能继续参与自动流程。
2. B 发起自动接续请求，A 在全部页面保存得到确认、没有其他持续编辑者且后台任务允许时响应；或由用户在 A 点击“关闭本服务器”。复用当前停写、检查点、备份、清单。A 持久记录已停写，之后即便请求失败也不恢复编辑。
3. A 用原 owner/sequence 作条件，发布 `sealed(sequence+1, handoff_id, manifest_digest)`。操作 ID 保持不变；响应丢失时读回确认同一操作是否成功，不能盲目再生成新交接或宣称失败后恢复写入。
4. B 在线读取协调器指定的 seal，自动等待本地工作区与指定清单一致；旧副本、缺失文件、冲突、身份不符继续阻止编辑。只拿到编号不放行。
5. B 完成校验后，条件申请将相同 seal 变为 `active(B)`。与本地 `activating/active` 回执衔接，成功并持久化后才构造可写 Stores。两台同时接收时只有一台成功；原设备重新打开也走相同竞争规则。
6. 接收过程中崩溃或网络响应不明时保留可恢复状态，通过 owner、操作 ID、本机回执和 manifest 重新核对。无法判明时停写，不凭时间戳选择一方。

**关键限制：** 第一版不按“心跳超时”“另一台离线多久”转移所有权。离线/休眠不等于原设备已停写；过期云端租约也阻止不了原进程恢复写入。要支持强制自动接管，须另外设计所有写入口可执行的 fencing（旧持有者永久失去写资格），本次不建议纳入。

## 两台不同时在线时

| 情形 | 能否自动接班 | 原因 / 建议行为 |
| --- | --- | --- |
| A 已完成停写、在线发布，文件也上传齐；之后关机，B 稍后上线 | 可以 | 协调服务保留 seal；两台无需同时在线 |
| A 在线发布 seal，但大素材尚未上传就断网/关机 | 不一定 | B 继续等缺失文件；协调记录无法搬运留在 A 的字节 |
| A 仅本地封存，发布请求未完成 | 不自动放行 | 仍需 A 恢复联网并完成发布，或明确的人工恢复流程 |
| A 在线且程序可响应，B 启动 | 可以请求协作交接 | A 保存并排空成功后才交出；忙碌或无法保存时等待，不能强占 |
| A 异常退出或程序无法响应，B 启动 | 不自动接管 | 没有完成交接的证据，不能把离线推断成结束编辑 |
| B 当前离线 | 不进行新的自动所有权转移 | 无法查询/条件更新权威状态；是否允许已有 owner 离线继续须单独定义 |
| 协调服务暂时不可用 | 暂停新的交接/接班 | 保留当前数据与回执，恢复后核对并重试 |

这些限制是方案逻辑推导：如果任何渠道都没把 A 最新状态/内容传出来，B 无法凭自身旧副本证明 A 的最终版本。

## 实施前的最小验证清单

- 先确认两台系统、OneDrive 账号类型、是否同账号/共享目录，以及可接受的联网和服务维护成本。
- Graph 路线先验证实际账号的权限和条件更新，不用手工序列请求代替真实两端竞争测试。
- 验证 A 发布后立即断网、请求成功后响应丢失、B 验收后抢占失败、休眠恢复、双方同时启动、旧 seal 回放、旧客户端启动。
- 沿用当前待完成的真实双设备 OneDrive 验收，包括延迟、Files On-Demand、冲突副本、大素材和 Windows 行为。
- 本次仅研究并核对文档/代码，未操作用户工作区数据，未配置 Microsoft 登录、部署协调器或实测 Graph。
